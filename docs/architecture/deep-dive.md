# qwen-audio-agent 架构

本文档定义了产品边界。与这些不变量相悖的更改属于架构变更，而非局部功能开发。

关于目标边界以及实时语音聊天机器人、异步任务桥接和单一用户配置的后端代理的分阶段重构，请参阅
[实时语音聊天机器人运行时路线图](https://github.com/QwenAudio/qwen-audio-agent/blob/main/docs/roadmap/frontend-chatbot-runtime.md)。
在路线图的每个阶段完成之前，本文档仍是对当前运行时行为经过测试的描述。

## 1. 用户可见模型

用户与一个 qwen-audio 助手对话。在内部，存在两个 qwen-audio-agent 层：

1.  **实时前端** — 全双工语音、自然对话、时间和记忆，以及可配置的轻量级工具，如检索。
2.  **后端代理** — 一个已配置的操作代理，负责处理需要在用户环境中执行操作、持续运行或创建交付物的请求。

后端可以是 ACP 代理，如 OpenCode、OpenClaw、Qoder、Qwen Code、MiniMax Code、Kimi Code 或 Pi；也可以是远程 A2A 代理；或自定义的 BackendPort 适配器。它可以在内部使用工具、技能、代理或其他会话。这些属于后端私有实现细节，不会创建额外的 qwen-audio-agent 层。协议细节保留在 ACP、A2A 或自定义 BackendPort 适配器内部；后端特定的启动和能力行为存在于注册的驱动程序中。

## 2. 非阻塞请求流程

```text
最终 ASR
   │
   ├─ 可立即回答 ───────────────────────────► 实时语音
   │
   └─ 需要工作
          │ spawn_thinking(目标)
          ▼
      任务已接受
          │ 响应立即返回给实时前端
          ▼
      所有者 FIFO 队列
          │
          ▼
      已配置的 BackendPort
          │ 后端决定如何工作
          ▼
      最终呈现
          │ 等待安全的双工插入窗口
          ▼
      实时前端自然地说出结果
```

`spawn_thinking` 从不等待所请求的工作。当多个任务项排队时，用户可以继续说话。对于每个所有者，一次只会将一个任务项发送到已配置的 BackendPort。

## 3. 实时边界

实时前端可以组合可用的工具来完成有界请求；单独的多次工具调用不需要后端执行。工具分为两个提示词所有权类别：

| 契约 | 工具 |
| --- | --- |
| 核心契约 | `spawn_thinking`, `get_agent_task_status`, `cancel_agent_task`, `respond_permission`, `respond_agent_input`, `get_current_time`, `memory` |
| 可选能力 | `web_search`, `fetch_url`, `knowledge`, `recall`, `notes`, `schedule_reminder`, `enter_sleep`；动态 MCP 工具也依赖于配置 |

固定的 `config/frontend-agent/PROMPT.md` 只能提及核心契约工具。它负责稳定的对话、工作确认和结果、取消、确认以及记忆持久化工作流。可选工具带有其自身的目的和调用条件；固定提示词和核心工具均不得引用它们。可选工具之间也不能硬编码彼此的名称。字段含义和输入规则属于工具 Schema；接收或交付特定的指令属于相应的事件。网关独立于模型合规性来强制执行可用性、权限和执行验证。

核心与可选是一种提示词维护约定，而非运行时分类；核心工具允许列表仅存在于边界测试中。注册表存储工具定义以及可选的、有效的运行时策略，例如能力要求、结果大小限制和重复处理。工具不需要分组或执行模式标签。未配置的后端会隐藏 `spawn_thinking`；确认工具仅针对真实的待处理请求暴露。即使是核心契约工具，在不可用时也无法被调用。测试检查固定提示词、工具引用和能力开关，以将新的可选功能排除在核心规则之外。

网关为待处理的后端权限暴露 `respond_permission`。模型回答权限请求；网关在转发决策之前解析该请求及其关联的任务。

`memory` 通过一个扁平接口维护两个普通的 Markdown 文档。每次调用都是一个原子的 `read`、`append` 或 `replace` 操作。`replace` 定位一个唯一的源片段，如果该片段缺失或存在歧义，则会安全失败。实时前端可以在单轮中发出多次调用；网关合并它们的后续响应。这两个文档具有不同的权限：

- `user` 是当前用户的长期个性化覆盖层：称呼方式、关系、助手为该用户设定的名称、语言、表达风格和默认行为。它作为用户授权的指令材料被注入，覆盖来自 `ASSISTANT.md` 的实例级默认值，并让位于用户当前的表述。
- `memory` 包含用于理解和回答的持久化事实和决策，绝不作为指令。这两个范围通过行为权限而非主题进行区分。

两个范围都不能授权泄露内部结构、跳过权限检查或更改任务和安全协议。打包的 `PROMPT.md` 仍然是核心策略，不能被个性化覆盖。本地的 `ASSISTANT.md` 仅包含助手实例的默认身份、个性、关系立场和表达风格。助手永远不会通过 memory 编辑它。它由打包模板创建一次，在升级过程中保留，并在编辑后为下一个语音会话重新加载。

除了显式的工具写入之外，会话结束提取器会协调遗漏的显式用户指令和持久化事实。它将前者路由到 `USER.md`，将后者路由到 `MEMORY.md`，通过实时工具使用的相同上下文服务进行。它从不直接写入文件或修改 `ASSISTANT.md`，拒绝文档边界错误和敏感内容，在本地审计文件中记录结果，并在未配置文本模型 API 密钥时静默禁用自身。

`notes` 管理用户命名的列表（购物清单、待办事项、阅读列表），作为前端拥有的易失性集合：单次调用的添加、显示、匹配移除、清空和删除，无需后端参与。列表是项目数据，而非记忆；稳定的事实保留在 `memory` 中，列表项永远不会被写入用户偏好或事实记忆。项目和列表的解析首先匹配精确文本，然后是唯一的不区分大小写的子字符串，否则将候选名称的歧义报告回模型以进行澄清。`clear` 和 `drop` 额外要求在当前轮次中有明确的破坏性意图。

`get_agent_task_status` 是实时前端查询生命周期、进度和中间结果的唯一入口点。网关直接读取其自身的任务记录，包括最新的适配器规范化消息、活动和产物描述符。状态检查不会创建另一个任务、调用协调器或进入异步通知队列。

它没有用于以下操作的工具：

- 选择、创建、继续或取消后端会话；
- 选择同步、异步、前台或后台执行；
- 选择后端执行策略；
- 选择工具、代理或子代理。

`respond_permission` 是“实时前端不控制执行策略”这一规则的唯一例外。它只能转发当前轮次用户对网关提供的、待处理的、所有者范围内的权限请求的明确决定。它可以理解自然的肯定或否定措辞，例如“可以”或“不允许”，但不能在没有当前轮次用户表述的情况下凭空创造同意、创建请求、选择工具或修改后端权限策略。模型、卡片和网关共享一个简短的 `permission_id`，没有单独的面向模型的别名。对于单个待处理请求，只需 `decision`；多个请求则需要显式的 `permission_id`。无效的 ID 永远不会回退到授权另一个请求。通知保留 `task_id` 以提供上下文，但调用无需重复它。同一用户轮次中的重复确认会复用回执，而不会扩大其授权范围。适配器私下映射原始的 ACP 选项 ID。内置的 ACP 适配器使用随机的短 ID，而不是重新启动可能与会话上下文冲突的计数器。回复使用 `task`、`always` 或 `reject`：允许此任务及其后续操作，允许此前端会话中的跨任务操作，或拒绝当前操作。网关的任务层 PermissionPolicy 由语音、客户端命令和计划工作共享。它根据 BackendPort 的每操作 `once` 决策批准后续请求，包括已排队等待已批准任务的请求。任务授权在完成、失败或取消时过期，并且永远不会转移到另一个任务。两个范围都不会创建持久化的后端规则，也不会在网关重启后存活。权限、进度和恢复上下文的协议信封完全由网关拥有。模型创建的仿冒品不是事件，不能启用其关联的工具，也不会持久化到对话历史中。

传递给 `spawn_thinking` 的 `objective` 是对用户请求的保守解释，而非执行计划。它必须在提交前将诸如“继续那个页面”之类的引用解析为一条自包含的指令。该指令是发送到后端的唯一模型可见任务文本；逐字的 ASR 不会作为第二个任务描述附加。后端代理不会收到前端人设、持久记忆或最近的聊天历史。与执行相关的事实必须被解析到指令中，而不是转发这些文档。

后端轮次可能返回结果，或请求继续所需的信息、选择、确认或澄清。前端自然地呈现该需求。当用户回答时，它再次调用 `spawn_thinking` 作为同一工作的延续，而不是预测或模拟下一个后端操作。此规则不依赖于特定案例的措辞。

网关自动将当前轮次的附件作为原生协议部分携带，绝不作为模型可见的 JSON 清单。只有明确依赖于早期图像或文件的工作才使用可选的 `input_refs` 字段和会话本地的输入 ID。任务 ID、所有者身份、生命周期、时间戳和路由仍然是结构化的网关/BackendPort 数据，不会放入后端代理的指令中。工作目录和用户时区不会在每个提示词中重复；协议或后端运行时上下文拥有它们。

## 4. 固定后端代理会话

ACP 适配器为每个所有者和后端拥有一个持久的协调器会话身份：

```text
qwen-audio-agent:<所有者>:<后端>
```

网关在该稳定键后面存储原生 ACP 会话 ID，并在后续轮次中调用 `session/resume`。项目委派同样会在其记录的工作目录中恢复选定的原生会话，因此语音发起的工作保留在后端自身的会话历史中，而不是网关副本中。

语音浏览器会话 ID 和任务 ID 永远不会更改该身份。因此，新的语音对话会继续使用相同的后端代理上下文。

网关队列和 ACP 适配器都会序列化写入。这种双重保护可防止并发消息在单个后端会话内竞争。

后端代理拥有其执行策略。qwen-audio-agent 提供一条自包含的自然任务指令和当前轮次的原生附件；它不会转发前端历史或偏好、规定任务状态 JSON，也不会指示后端代理如何使用后端特定的能力。

## 5. 任务状态

qwen-audio-agent 任务记录是交付回执，而非后端内部任务图的镜像。

```text
queued → running ─────────────────────────→ completed
   │        └→ delegated → finalizing ────────┘
   └────────────→ cancelling → cancelled
                            ↘ failed
```

公共字段仅限于用户请求、时间戳、最终结果/错误、通用活动、带有可选安全操作细节的有界待处理权限摘要以及通知状态。没有执行模式、交付模式、子代理状态、后端权限标识符、后端拓扑或后端取消内部细节。

UI 将 `queued` 和 `running` 都显示为相同的“处理中”状态。队列位置是内部调度细节，不会改变用户的双工对话。

排队和直接运行的任务在网关重启后无法安全恢复，因此它们会因明确的“重启”原因而变为失败状态。委派的任务只有在适配器能够验证持久化的原生会话时才能重新附加。已完成的结果和通知投递状态会被持久化。

## 6. 进度动画

进度是可见性，而非控制。ACP 适配器将标准的 `session/update` 通知投射为通用活动：

- 工具名称、有界的用户安全细节以及运行/完成状态；
- 计划进度；
- 不包含思考内容的通用思考信号；
- 有界的会话标题和当前模式元数据。

UI 将其映射到稳定的任务目标或诸如“搜索中”、“阅读中”、“正在生成图像”或当前模式等短语。通用思考信号会持续显示任务目标。所有活跃的后端工作，包括思考，都共享桌面宠物的 `working` 呈现；`processing` 呈现保留给前台实时轮次。会话 ID、子代理 ID、原始权限载荷和原始思考内容不会显示。待处理的权限可能会显示有界的标题、描述、命令或路径，这些是用户在机密类值被编辑后做出知情同意所必需的，但它不会引入单独的代理动画状态。

活动永远不会产生语音状态更新，也永远不会影响队列。

## 7. 最终结果交付

后端代理返回标准的 ACP 轮次。文本通过 `agent_message_chunk` 更新到达，而图像、音频和资源则保持为原生 `ContentBlock` 值；轮次以 `session/prompt` 的 `PromptResponse` 结束。ACP 适配器不再扁平化这些值或要求模型重建专有的结果信封。它将文本和非文本内容投射到 BackendPort 的 `content` 和 `artifacts` 字段中，网关仅接受 `stopReason=end_turn` 作为成功完成的轮次。取消、拒绝以及令牌或代理请求限制会进入网关的已取消或失败路径。然后，网关为每个客户端选择合适的对话、资源和语音呈现。

已完成的结果优先于原始对话。在新连接上，可以恢复来自旧对话的未完成结果（针对同一所有者）。可续期的声明可防止两个实时前端呈现相同的结果。结果被注入到实时上下文中，并仅在播放完成后标记为已交付。如果用户打断、正在说话或有另一个响应待处理，则交付会等待并重试，而不会重复添加上下文。重试次数有限，因此单个格式错误的结果不会阻塞后续的完成。

当后端代理调用 `session_start` 或 `session_send` 时，只有在会话工具创建或继续目标工作并返回经适配器验证的运行和会话标识符后，委派才会建立。它不是由模型编写的字段建立的。ACP 忠实地携带工具调用、工具结果和轮次终止；适配器将验证过的关联发布到 TaskManager，后者将原始任务移动到 `delegated` 状态，并释放后端代理序列化锁和任务调度器通道。因此，其他语音请求可以在目标会话运行时使用协调器。

协调器可以在工具成功后自然结束其 ACP 轮次，但该文本既不控制任务状态，也不作为完成信号。关联 ID、目标会话和生命周期保留在网关任务注册表和适配器运行时中；模型无需回显它们。

适配器独立地保持任务生命周期和事件订阅的活跃。只有与委派 ID 关联的匹配 ACP 目标提示词完成才能推进任务。然后，适配器会短暂地重新获取后端代理锁，并发送验证过的结果（包括其原生 ContentBlocks），以进行最终的自然回答。繁忙的目标、空结果、无关的会话更新或较旧的结果都无法完成任务。

ACP 代理轮次没有人为的挂钟截止时间。初始协调器轮次、委派的目标轮次和最终的综合轮次仅在 ACP 报告完成、用户明确取消任务或后端退出或关闭时结束。连接初始化和有界的控制 RPC 保留超时，以便不可用的后端不会无限期地阻塞网关启动。

取消是确认式的，而非乐观式的。`queued` 任务在本地取消。`running` 或 `finalizing` 任务会中止其活跃的后端请求。对于 `delegated` 任务，首先要求空闲的协调器调用 `session_cancel`；如果协调器会话被占用，则 ACP 适配器直接向精确关联的目标会话发送 `session/cancel`。任务保持 `cancelling` 状态，直到这些路径之一确认停止，然后变为 `cancelled`。失败的停止会变为 `failed` 状态并带有取消错误。在适配器直接中止后，网关记录一个取消事实，并在下一个安全的协调器轮次中注入一次。这协调了协调器的历史，而不会延迟取消或重复停止操作。

前端确认来自网关实际接受的任务，而非协调器编写的委派状态。协调器轮次仍根据 ACP 生命周期信号结束；网关不会从确认文本或成功的会话工具调用中推断其完成。

## 8. 后端内部能力

对于接受客户端提供的 MCP 服务器的 ACP 后端，包括 OpenCode、Qoder、Qwen Code、MiniMax Code 和 Kimi Code，网关会向协调器注入相同的五个工具：会话列表、启动、发送、状态和取消。OpenClaw ACP 不接受客户端提供的 MCP 服务器，因此相同的协调契约映射到 OpenClaw 的原生会话工具。`session_start` 和 `session_send` 返回一个不透明的委派 ID。在任一操作成功后，后端代理不得轮询、重复工作或根据自身上下文回答；适配器负责等待、取消、权限路由和结果关联。

协调器 MCP 服务器还通过 MCP 初始化的 `instructions` 字段发布稳定的协调契约。其驱动程序声明了 `coordinatorMcpInstructions` 的后端在每轮中仅接收动态的自然任务指令；这避免了将相同的路由和响应规则附加到持久化的会话历史中。仅当已验证代理主机能将 MCP 服务器指令投射到模型上下文后，此能力才会启用；目前适用于 OpenCode、Qoder、Qwen Code 和 Claude Code。共享载荷保持在 2 KiB 的可移植性预算内。未经验证的代理——或未来超过该预算的载荷——保留完整的每轮提示词作为安全回退。此标志不描述通用的 MCP 支持。项目会话永远不会收到协调器 MCP 服务器。

`session_status` 仅用于观察。如果查询失败，后端代理必须报告失败；它不得使用原生工具检查目标目录或复制委派的工作。

前端代码不得依赖于选择了哪种内部能力。前端任务快照只能暴露有界的标题和通用的委派状态，绝不能暴露委派 ID、目标会话 ID、目录或原始事件。

## 9. 依赖方向

```text
WebUI / TUI / Desktop
   ↓ WebSocket 和 HTTP
实时网关
   ↓ spawn_thinking
任务队列
   ↓
结构化的 BackendPort 任务
   ↓
适配器投射：自然指令 + 原生附件部分
   ↓
OpenCode ACP、OpenClaw ACP 桥接、Qoder ACP、
Qwen Code ACP、Kimi Code ACP 或其他 ACP 代理
```

后端特定的 API 细节仅存在于 `server/src/agent` 中。实时工具不得导入后端适配器。UI 仅消费公共的任务和会话事件。包级别的 `shared` 模块是基础的运行时工具；服务器 `core` 和 `process` 可以依赖它们，但它们不得依赖服务器层。

`server/src/client` 拥有北向客户端事件注册表、运行时命令应用服务、`ClientActionPort
