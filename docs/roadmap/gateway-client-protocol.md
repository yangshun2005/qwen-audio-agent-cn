# 网关客户端协议路线图

> 状态：提案
>
> 跟踪：[GitHub Issue #251](https://github.com/QwenAudio/qwen-audio-agent/issues/251)
>
> 规范：[网关客户端协议](../gateway-protocol.md)

## 目标

完成 qwen-audio-agent 剩余的公共架构边界。`BackendPort` 已经将网关与 ACP、A2A 及自定义后端代理隔离开来。本路线图将网关核心与 TUI、WebUI、Desktop Orb 以及未来的客户端环境隔离开来。

由此产生的框架具有三个可替换的边缘：

```text
客户端环境
        ↕ 网关客户端协议 / ClientPort
网关核心
        ├─ RealtimeProvider
        ↕ BackendPort
后端代理
```

## 当前基线

该仓库目前已有：

- 一条 WebSocket 承载语音、文本、播放回执、Task 事件和状态，而某些运行时命令仍使用内部 REST/SSE 路由；
- 共享的事件常量和 Zod 消息 Schema；
- 专用的用户输入运行时；
- 标准化的 BackendPort 事件和 Task 投影；
- 与提供商无关的结果和权限注入原语；
- Task 公告排队、重试和播放确认；
- 第一方 WebUI、TUI 和桌面客户端。

剩余差距包括：

- 客户端分发仍集中在 `realtime-gateway.mjs` 中；
- 桌面能力和休眠行为仍作为特殊情况处理；
- 不存在通用的网关到客户端操作/结果契约；
- 第一方客户端在某些 Task 控制、权限、会话历史和恢复流程中仍使用内部 REST/SSE 别名；
- 用户输入、Task 公告、权限和网关触发器尚未共享一个语义事件/投递边界；
- 重放、完整的第一方迁移以及完整的客户端一致性测试套件尚未实现。

## 架构规则

1. 每个网关保持一个活动客户端。
2. 保持原始媒体数据不进入语义事件路由器。
3. 保持用户输入、客户端事件、Task 事件和客户端操作权限相互独立。
4. 由网关策略决定模型可见性和响应时机。
5. 在提供商编码之前，将语义事件投影为与提供商无关的代理投递值。
6. 根据协商的客户端操作能力派生模型可见的客户端工具。
7. 使用单一 WebSocket 运行时控制平面；REST 仅用于发现、健康检查、静态配置和主机管理。
8. 拥有每个公共网关类型，同时在语义匹配的情况下，有意识地使熟悉的字段名称和载荷形状与外部标准保持一致。
9. 将上下文来源保持在单一活动客户端之后，而不是添加第二个连接角色。
10. 在所有第一方客户端完成迁移之前，保持每个阶段的向后兼容性。
11. 每个阶段作为独立可审查的 PR 落地，并关联到 Issue #251。

## PR 策略

- 不要在一个 PR 中同时进行协议版本迁移、事件入口、代理投递和客户端操作迁移。
- 每个 PR 关联 Issue #251 并标识其 GCP 阶段。
- 每个新的公共事件都附带 Schema、解析器、负面测试、能力行为和文档。
- 在移除兼容性别名之前，现有第一方行为必须保持正常。
- 任何阶段不得将 Realtime 提供商、ACP、A2A、Electron、React 或 CoreAudio 的线上对象泄漏到公共端口。允许网关规范中记录的语义字段名称和载荷形状对齐。
